AI agent action authorization API

Decide whether an AI agent may take a consequential action—before it runs

For platform, security, AI-governance, and workflow engineering teams placing payments, procurement, account, or data actions behind explicit authority. Verify the proposed action against a signed, expiring mandate and receive an allow, deny, or requires-approval receipt.

Who this is for and when to use it

A procurement agent proposes a $300 transfer to an approved vendor: it is under the hard cap but over the threshold that requires a human approval.

Best-fit team

Platform and security engineers adding a pre-execution authorization boundary to agentic workflows with consequential side effects.

Input

Principal, agent identity, expiry, grants, resources, amount limits, approval threshold, and the concrete action being proposed.

Output

allow, deny, or requires_approval, with stable violation codes and a decision receipt.

Primary-value event

After issuing a signed mandate, a successful authenticated POST /v1/verify returning a machine-actionable decision and receipt.

Copyable no-account path

Generate a future expiry and run the demo

This block needs Python 3 and curl, replaces no credential, and creates a UTC expiry 24 hours ahead so the mandate is valid when you run it.

python3 -c 'import json; from datetime import datetime,timedelta,timezone; print(json.dumps({"mandate":{"principal":"user_8814","agent":"agent_procurement_v3","expiresAt":(datetime.now(timezone.utc)+timedelta(days=1)).isoformat(timespec="seconds").replace("+00:00","Z"),"currency":"USD","totalSpendCapMinor":500000,"grants":[{"action":"payments.transfer","resources":["vendor.acme"],"maxAmountMinor":100000,"approvalRequiredAboveMinor":25000}]},"action":{"agent":"agent_procurement_v3","action":"payments.transfer","resource":"vendor.acme","amountMinor":30000,"currency":"USD"}}))' |
curl -sS -X POST https://agentmandate-api.com/v1/demo/verify \
  -H 'content-type: application/json' \
  --data-binary @-

Expected contract-shaped result

What first useful value looks like

Representative response
{
  "count": 1,
  "allowed": 0,
  "denied": 0,
  "requiresApproval": 1,
  "receipts": [{
    "decision": "requires_approval",
    "violations": [{"code": "approval_required"}],
    "digest": "sha256:example_receipt_digest"
  }],
  "requestId": "req_example"
}

The digest and request ID vary. The decision, counters, violation code, and receipt structure are the contract-shaped result to consume.

First useful result

requires_approval means the grant matches the action and resource, but amountMinor: 30000 exceeds the mandate's approvalRequiredAboveMinor: 25000.

Interpretation

Your caller can branch safely: execute only on allow, stop on deny, and route requires_approval to your own approval system. The API does not execute the transfer.

Authenticated first-value path

Verify the account, issue a real signed mandate, then verify its action

  1. Request and claim a product-scoped key.

    Replace only the email and one-time email token, then keep the returned API key out of source control.

  2. Issue a signed mandate with /v1/mandates.

    The copied command generates a future expiry. Capture the exact returned mandate and signature; do not fabricate or edit them.

  3. Verify that exact signed object at /v1/verify.

    A successful decision receipt is the primary-value event. Key issuance or mandate creation alone is not activation.

curl -sS -X POST https://agentmandate-api.com/v1/keys \
  -H 'content-type: application/json' \
  -d '{"email":"you@example.com","source":{"source":"product_site","medium":"exact_intent","campaign":"search-agent-mandate-exact-intent-v1","content":"ai-agent-action-authorization-api-v1"}}'

curl -sS -X POST https://agentmandate-api.com/v1/keys/claim \
  -H 'content-type: application/json' \
  -d '{"token":"PASTE_ONE_TIME_TOKEN_FROM_EMAIL"}'

export KEY='PASTE_API_KEY_FROM_CLAIM_RESPONSE'

MANDATE_JSON="$(python3 -c 'import json; from datetime import datetime,timedelta,timezone; print(json.dumps({"principal":"user_8814","agent":"agent_procurement_v3","expiresAt":(datetime.now(timezone.utc)+timedelta(days=1)).isoformat(timespec="seconds").replace("+00:00","Z"),"currency":"USD","totalSpendCapMinor":500000,"grants":[{"action":"payments.transfer","resources":["vendor.acme"],"maxAmountMinor":100000,"approvalRequiredAboveMinor":25000}]}))')"

SIGNED_MANDATE="$(curl -sS -X POST https://agentmandate-api.com/v1/mandates \
  -H "Authorization: Bearer $KEY" \
  -H 'content-type: application/json' \
  -d "$MANDATE_JSON")"

VERIFY_BODY="$(printf '%s' "$SIGNED_MANDATE" | python3 -c 'import json,sys; signed=json.load(sys.stdin); print(json.dumps({"mandate":{"mandate":signed["mandate"],"signature":signed["signature"]},"action":{"agent":"agent_procurement_v3","action":"payments.transfer","resource":"vendor.acme","amountMinor":30000,"currency":"USD"}}))')"

curl -sS -X POST https://agentmandate-api.com/v1/verify \
  -H "Authorization: Bearer $KEY" \
  -H 'content-type: application/json' \
  -d "$VERIFY_BODY"

After the example works

Put verification immediately before one controlled side effect

  1. Model one narrow grant.

    Name the concrete action and resource; add the smallest useful amount, count, expiry, and approval limits.

  2. Branch on the receipt.

    Allow only an allow decision. Send requires_approval to your human workflow and stop on deny.

  3. Retain the receipt with your action audit.

    Track prior spend and counts in your own system, then verify again for each proposed action. Mandates are stateless.

Troubleshooting

The three most likely blockers

401 unauthorized

Use the API key returned once by /v1/keys/claim, not the email claim token. Send it exactly as Authorization: Bearer $KEY.

400 invalid_request or client-side 422

For authenticated verification, pass the exact mandate and signature returned by /v1/mandates. Do not edit signed claims. Expiry must be a future RFC 3339 timestamp.

429 rate limited

Read Retry-After when present, wait, then retry with bounded exponential backoff. Do not retry a denied action as if it were a transport failure.

Need support?

Record the stable error.code and request ID. Share the request ID only—never a key, claim token, approval token, or signed production mandate.

Trust, privacy, and limits

Authorization is a decision boundary, not action execution or identity proof

The keyless demo uses a throwaway signing key, stores nothing, and produces a signature that cannot be used on the authenticated endpoint. Authenticated use is governed by the privacy policy and terms. Minimize mandate metadata and keep production credentials and approval tokens out of examples and logs.

  • The API evaluates only the mandate, action, policy, and state values you supply. It does not prove that a user actually authorized those inputs.
  • It does not execute payments, procurement, account changes, or data operations; your controlled system remains responsible for the side effect.
  • No customer or revenue result is claimed. A live page, demo receipt, package install, signup, key, or synthetic test is not commercial validation.
